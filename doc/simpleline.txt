INTRODUCTION                                         *simpleline-introduction*

Simpleline provides a Vim9script statusline and buffer-oriented tabline. The
core UI requires Vim 9.1 with +vim9script. Git queries run in an asynchronous
Rust daemon and additionally require +job, +channel, Git, and Rust/Cargo 1.88
or newer for building. +timers is needed only for polling. Neovim is not
supported.

Dynamic text (filenames, refs, provider text) is escaped before it reaches the
statusline parser. Disabling Simpleline restores the global and per-window
options that it replaced.

Beyond mode/file/Git/position, the statusline can show a search count while
'hlsearch' highlighting is active, a REC @reg indicator while recording a
macro, error/warning counts from an auto-detected diagnostics provider
(coc.nvim, ALE, or vim-lsp — first match wins), and the simpleremote
workspace you are connected to (see |simpleline-simpleremote|). The tabline
accepts mouse clicks: left click switches to the clicked buffer, middle click
deletes it when it has no unsaved changes.

The Git segment also names an operation that needs attention — REBASE, MERGE,
CHERRY-PICK, REVERT, BISECT, or AM — and keeps it visible in compact windows.

INSTALLATION                                         *simpleline-installation*

For vim-plug: >

  Plug 'beamiter/simpleline', {'do': './install.sh'}
<
Or run `./install.sh` inside the plugin checkout. The script builds and
installs lib/simpleline-daemon. Git can be disabled before load: >

  let g:simpleline_git_enabled = 0
<
When `vim` is on PATH, the installer also generates help tags; otherwise it
prints the manual command. After a manual copy, run: >

  :helptags /path/to/simpleline/doc
<
Rerun the build/install step after every source update. Native Windows users
should build with `cargo build --release --locked` and copy
target/release/simpleline-daemon.exe to lib/simpleline-daemon.exe.

                                      |simpleline-simpleremote|)
g:simpleline_show_search              1 (current/total while v:hlsearch)
g:simpleline_search_maxcount          99 (0 counts every match)
g:simpleline_search_timeout           20 ms (0 or less never gives up)
g:simpleline_show_recording           1 (REC @reg while recording)
g:simpleline_show_diagnostics         1 (E:n W:n from coc/ALE/vim-lsp)
g:simpleline_filename_mode            'native' (native, tail, rel, abbr, abs)

The default "native" keeps Vim's %f behavior.  "rel" and "abbr" use the
current SimpleTree root when available, otherwise the current window's cwd;
outside-root files fall back to their basename.  Unnamed and special buffers
keep Vim's native labels.  The one exception is a simpleremote remote://
buffer, which every mode — "native" included — renders relative to the
remote workspace root (see |simpleline-simpleremote|).

g:simpleline_filetype_icons           {}

g:simpleline_debug                    0

When statusline management is enabled, Simpleline raises 'laststatus' to 2 if
needed and restores the old value on disable. Compact mode keeps the branch and
position while hiding file metadata, Git counts, and ahead/behind. Under
'laststatus' = 3 the compact threshold is compared against &columns, because
Vim draws a single statusline across the whole screen there; otherwise it is
compared against the width of the window being drawn.

REDRAW CACHES ~
                                                 *simpleline-redraw-caches*
'statusline' is a %! expression, so the whole line is rebuilt on every redraw
— that is, on every cursor movement. Two segments used to do real work there
and are now memoized:

- The search count is cached on everything searchcount() reads: the buffer,
  b:changedtick, @/, the cursor position, v:hlsearch, 'ignorecase',
  'smartcase', and the two budget options above. A recompute that exceeds
  g:simpleline_search_timeout is reported as no count, and that pattern is not
  retried in that buffer — one pathological pattern degrades once instead of
  on every frame. Clear the state with :SimpleLineReload.
- The diagnostics counts are cached on the buffer, b:changedtick and
  b:coc_diagnostic_info (coc.nvim publishes into a buffer variable, so its
  exact input is cheap enough to keep in the key). ALE and vim-lsp cost a
  function call and are not in the key; they publish asynchronously without
  touching b:changedtick, so Simpleline listens for User CocDiagnosticChange,
  ALELintPost, ALEJobStarted and lsp_diagnostics_updated. A provider that
  publishes none of these can show a count that is stale until the next edit
  or buffer switch.

:SimpleLineDebug reports the hit rate of both caches.

GIT ~
g:simpleline_git_enabled              1
g:simpleline_git_interval             2000 ms; minimum 250; 0 is event-only
g:simpleline_git_watch                1 (let a capable daemon report changes)
g:simpleline_git_show_status          1
g:simpleline_git_show_operation       1 (show REBASE/MERGE/etc.)
g:simpleline_git_provider             'auto' ('daemon', 'simplegit')
g:simpleline_show_hunks               0 (per-file +/~/- lines from simplegit)
g:simpleline_daemon_path              '' (search runtimepath/lib)

The Git segment shows the branch, ahead/behind, added/modified/deleted
counts, conflicts as !n, and stashes as $n. Stash counting requires Git 2.15
(--show-stash); the daemon probes `git --version` once and skips the flag on
older installations. Compact windows keep the branch, operation, and
conflicts. A `git status` that fails inside a repository is reported as an
error, not as "not a repository", so a transient failure keeps the last
known-good segment instead of blanking the branch and operation. Operation
detection reads Git's sentinel files and starts no extra process. Directory symlinks are resolved before repository discovery; an
unresolvable physical path reports no operation instead of consulting a
possibly unrelated lexical parent repository.

WATCHING                                            *simpleline-git-watch*

A daemon advertising the "watch" capability is asked to report a directory's
changes instead of being asked for them every g:simpleline_git_interval. A
watched directory is not polled at all: the daemon watches the worktree,
coalesces bursts of filesystem events, re-runs `git status` only when
something changed, and pushes an unsolicited git_info event. Buffer entry,
write, directory change and focus still request a refresh, so a repository
change is never waited for.

Watching is refused — and the directory keeps being polled exactly as before
— when the path is outside a repository, when the worktree has more than 4096
directories (a recursive watch costs one inotify descriptor per directory, a
finite per-user resource), when the platform watcher cannot start, or when
the daemon already watches 16 directories. In the last case the oldest watch
is withdrawn, the daemon says so, and that directory goes back on the poll.
A withdrawal is the price of a watch that is granted, and of nothing else: a
refused watch withdraws no directory, so an over-sized or unwatchable worktree
never costs a repository that is already watched. This matters because a
refusal is not retried until the daemon restarts.

Unsolicited events are the one exception to "every reply is correlated to its
request by id". They carry id 0 and are correlated by path instead, against
the directories this client asked to watch and the daemon confirmed; an event
for anything else is discarded.

A push answers no request, so whether the daemon should collect the per-file
paths travels with the watch itself (see |simpleline-tabline-git-status|). A
watched directory sends no further request that could carry a changed answer,
so the watch is re-sent whenever g:simpletabline_git_status or
g:simpleline_tabline turns the marks on or off — within one
g:simpleline_git_interval at the latest, and without the watch being dropped.

:SimpleLineHealth reports "git watch: on/negotiated, N dir(s) watched" and
whether the current directory is watched or polled.

Set g:simpleline_git_watch to 0 to keep the poll — worth doing on a
filesystem whose change notifications are unreliable, such as some network
and container mounts.

PER-FILE GIT STATUS ~
                                              *simpleline-tabline-git-status*
With g:simpletabline_git_status the tabline colours each buffer by the state
of its file in the repository the current buffer belongs to:

  SimpleTablineGitModified   changed, linked to DiffChange
  SimpleTablineGitAdded      untracked or newly added, linked to DiffAdd
  SimpleTablineGitDeleted    deleted, linked to DiffDelete
  SimpleTablineGitConflict   unmerged, linked to Error

The current buffer keeps SimpleTablineActive: which buffer you are in matters
more than its Git state. g:simpletabline_git_status_icons adds a glyph per
state ('M', 'A', 'D', 'U') when a colour alone is not enough; it is empty by
default because a glyph costs tabline width. Buffers belonging to another
repository, and buffers with no file, carry no mark.

With g:simpleline_separator 'arrow' or 'round', the wedge between two items is
drawn in the left one's background over the right one's, so a marked buffer
needs transitions the fixed SimpleTab*To* groups cannot express. Those pairs
get a group synthesized from the two neighbours, named SimpleTabX<left>To<right>
(for example SimpleTabXFillToGitModified), rebuilt on |ColorScheme|. Pairs that
involve no Git group keep their own named group, so a hand-written override of
SimpleTabActToInact and friends still applies.

This needs a daemon that advertises the "git-status" capability, which means a
binary built from this version — run ./install.sh, then :SimpleLineRestart. An
older binary is never asked for the data and everything else keeps working;
:SimpleLineHealth reports "git file status: on/unavailable" in that case. Paths
are capped at 2000 per repository, after which health says "(truncated)".

The paths are only requested while something can paint them. With
g:simpletabline_git_status off — or with g:simpleline_tabline off, which means
no tabline is rendered at all — the request carries no "want_files" and the
daemon collects nothing; the Git segment of the statusline is unaffected.
Turning either option on or off after the fact takes effect on a watched
directory too: the watch is re-sent with the new answer (see
|simpleline-git-watch|). The first half of health's "git file status:" line
answers "would anything paint a mark", the second "can the daemon supply one".

INTEGRATIONS                                         *simpleline-integrations*

When simpletree#GetRoot() exists it supplies the path root. Otherwise cwd is
used when g:simpletabline_fallback_cwd_root is enabled.

                                                       *simpleline-simplegit*
simplegit publishes b:simplegit_status_dict — {head, ahead, behind, added,
changed, removed} — and simplegit#StatusDict() for the same data. When it is
installed, Simpleline takes the branch and ahead/behind from it rather than
having a second daemon run `git status` over the same worktree; its own daemon
remains the fallback and keeps supplying the file counts, conflicts, stash and
in-progress operation, which simplegit does not report. An empty head means
"not resolved yet" as much as "no repository", so it falls back rather than
blanking the segment. Simpleline redraws on User SimpleGitUpdate.

g:simpleline_git_provider selects the source:

  'auto'       (default) prefer simplegit, fall back to the daemon
  'daemon'     ignore simplegit entirely
  'simplegit'  ignore the daemon entirely (no file counts, conflicts,
               stash or operation, since only the daemon reports those)

Under 'auto' the daemon is still queried — it is the fallback, and it supplies
everything simplegit does not report. 'simplegit' is the one that stops the
second scan: the query is not sent, so no `git status` runs over the worktree
and the daemon is never spawned at all. The single exception is the tabline's
per-file marks (g:simpletabline_git_status), which read the daemon's reply
directly and are its only remaining consumer under this provider; while they
are on the query still runs, so the marks keep working. Turn them off — or
turn off g:simpleline_tabline — and nothing scans the worktree twice.
:SimpleLineHealth says which of the two it is as "daemon query: on/off" on the
Git provider line.

g:simpleline_show_hunks (default 0) adds a separate SimpleLineHunks segment
with simplegit's added/changed/removed *lines* for the current file, for
example `+12 ~3 -1`. It is off by default because it looks like the Git
segment's [+n ~n -n], which counts *files* in the worktree instead. It hides
in compact windows and renders nothing without simplegit.

A non-empty g:simplecc_status string is shown as a compatibility LSP/provider
segment. It is escaped and rendered literally.

                                                    *simpleline-simpleremote*
                                                    *g:simpleline_show_remote*
simpleremote connects Vim to an SSH host or a Docker container. Simpleline
needs nothing from it to load: every hook below is feature-detected at redraw
time and renders nothing when simpleremote is absent, so the default layout
is unchanged for everyone else.

The `remote` segment, second in the default left layout right after the
mode, shows the workspace g:SimpleRemoteStatusline() names — for example
`ssh:host:project@12ms`, the runtime latency arriving once the probe ran —
in the SimpleLineRemote group. While the connection is being made it reads
`connecting ssh:host:project`; disconnected, or with g:simpleline_show_remote
set to 0, it is empty. Compact windows drop the `@NNms` suffix the way they
drop ahead/behind. Simpleline redraws on the connection events (User
SimpleRemoteConnecting, SimpleRemoteConnected, SimpleRemoteWorkspaceChanged,
SimpleRemoteRuntimeReady, SimpleRemoteTreeRootChanged and
SimpleRemoteDisconnected), so a transition shows at once rather than on the
next cursor move. The segment is a layout entry like any other and can be
moved or dropped through |g:simpleline_sections|.

In simpleremote's virtual mode a remote file is a buffer named
remote:///abs/path with 'buftype' acwrite and b:vimrc_remote. Such a buffer
is treated as the file it stands for:

- The filename segment shows the remote path relative to the workspace root
  (g:simpleremote_workspace.tree_root, or root) in every
  g:simpleline_filename_mode — "native" too, since %f would print the whole
  URI; "tail" and "abs" apply as usual. A path outside the root, or a remote
  buffer of a session that has not reconnected yet, shows the whole remote
  path. %m and %r are kept.
- The tabline lists it (an ordinary acwrite buffer is still left out) and
  labels it under g:simpletabline_path_mode against the same remote root, so
  it can be picked and jumped to like a local file. The label cache and the
  render memo follow the remote root, so a workspace switch or a remote tree
  re-root relabels at once; after a disconnect the buffers stay listed under
  their basename.
- The Git segment asks the daemon nothing: `remote:///...` is not a directory
  anything local can run `git status` in, so no request is sent and no poll
  runs while such a buffer is current — the daemon is not even spawned on its
  account. What the segment shows is what simplegit publishes for the buffer
  in b:simplegit_status_dict (|simpleline-simplegit|), if anything.

In the projected modes (sshfs, docker-bind, local-map) remote files are
ordinary local paths under g:simpleremote_workspace.local_root and everything
works as it does locally, with one adjustment for sshfs: the mount is never
asked to be watched (a FUSE mount delivers no inotify events for edits made
on the remote side, so a granted watch would silence the poll for good) and
the timer polls a directory on it at most every 10 s, or every
g:simpleline_git_interval when that is longer — a `git status` there is a
network round trip per file. Buffer entry, write, focus and
:SimpleLineGitRefresh still ask at once.

:SimpleLineHealth prints "remote workspace:" — the status string the segment
keys on, the workspace mode, whether the segment is on and whether the
current buffer is remote — and says "remote, not queried" or "polled every
10000ms, sshfs" on the Git interval line.

                                                  *simpleline-custom-segments*
g:simpleline_custom_left holds user segments after Git/diagnostics and before
the filename. g:simpleline_custom_right renders between the LSP/provider
segment and the file metadata. Both use the same entry format: >

  let g:simpleline_custom_left = [
        \ {'fn': 'MyProjectStatus', 'hl': 'SimpleLineGit'},
        \ ]
  let g:simpleline_custom_right = [
        \ {'fn': 'MyVimrcStatus', 'hl': 'SimpleLineDiagWarn'},
        \ ]
<
Each entry is a dictionary:

  fn       Function name or Funcref taking no argument and returning a
           string.  An empty string hides the segment.  Required; an unknown
           function name is skipped silently, so a segment may be registered
           before its provider loads.
  hl       Highlight group, default SimpleLineMid on the left and
           SimpleLineRight on the right. Names outside \w\+ use that default.
  compact  1 (default) keeps the segment in compact windows; 0 hides it.

The returned text is escaped like every other dynamic segment, so a provider
cannot inject statusline format items.  A provider that throws is skipped and
reported through g:simpleline_debug; it never breaks the statusline.
Providers run on every statusline redraw, so they must be cheap — read a
cached variable instead of shelling out.  :SimpleLineHealth reports the total
registered/rendered count and the left/right registration split.

                                                       *simpleline-sections*
                                                       *g:simpleline_sections*
The statusline is a walk over a section layout, so the order of the segments —
and which of them appear at all — is configuration rather than code: >

  let g:simpleline_sections = {
        \ 'left':  ['mode', 'git', 'filename'],
        \ 'right': ['metadata', 'position'],
        \ }
<
"left" is packed against the left edge and "right" against the right; the %=
between them is the only thing the walk itself contributes. A side that is not
mentioned keeps its default, so overriding only "right" does not blank the
left. An explicit empty list is a layout rather than a missing one and clears
that side. A value that is not a dictionary, and a side that is not a list,
are ignored in favour of the default instead of breaking a redraw.

The built-in segment names, in default order:

  left     mode, remote, recording, git, hunks, diagnostics, custom_left,
           filename
  right    search, lsp, custom_right, metadata, position

custom_left and custom_right render g:simpleline_custom_left and
g:simpleline_custom_right in place, so the two mechanisms compose. Every
segment carries its own highlight group and separator glyph, which is why the
default layout renders exactly the line Simpleline drew before layouts existed.
Each segment still honours its own option: dropping g:simpleline_show_position
hides "position" wherever it is listed.

A name that matches no segment is skipped, the rest of the layout still
renders, and :SimpleLineHealth lists it under "segments unknown" — a typo is
otherwise indistinguishable from a segment that had nothing to say.

An entry can also be a segment dictionary in the |simpleline-custom-segments|
format, which needs no registration: >

  let g:simpleline_sections = {'left': [
        \ 'mode', {'fn': 'MyTicket', 'hl': 'SimpleLineGit'}, 'filename']}
<
                                                *simpleline#RegisterSegment()*
simpleline#RegisterSegment({name}, {spec}) gives such a dictionary a name a
layout can refer to. {name} must match \w\+ and {spec} is the same
{fn, hl, compact} dictionary, which must have an "fn". A registration cannot
take the name of a built-in segment: built-ins emit Vim format items on
purpose while a registered segment's text is always escaped, so shadowing one
would turn a layout into a way to inject format items. Rejected registrations
are reported through g:simpleline_debug.

                                                   *simpleline#SegmentNames()*
simpleline#SegmentNames() returns every name a layout can use, built-in and
registered, sorted. :SimpleLineHealth prints the same list next to the layout
it resolved for the current buffer.

                                              *g:simpleline_sections_filetype*
Per-buffer layouts are keyed by 'filetype' first and 'buftype' second, so one
entry can cover every scratch buffer without naming each filetype: >

  let g:simpleline_sections_filetype = {
        \ 'qf':     {'left': ['mode'], 'right': ['position']},
        \ 'nofile': {'left': [], 'right': ['position']},
        \ }
<
The first of the two keys that matches wins, and it is merged over
g:simpleline_sections side by side, exactly as that one is merged over the
default layout.

SimpleLine* highlight groups use `:highlight default`. Define them before
Simpleline to override the built-in palette. Tabline transitions derive from
TabLine, TabLineSel, and TabLineFill on ColorScheme.

TROUBLESHOOTING                                   *simpleline-troubleshooting*

No Git information        Run :SimpleLineHealth, :SimpleLineGitRefresh, then
                          ./install.sh if version/protocol stays unknown/0.
No per-file tabline paint :SimpleLineHealth reports "git file status:
                          on/unavailable" when the daemon predates the
                          "git-status" capability: run ./install.sh, then
                          :SimpleLineRestart.
Broken icon glyphs        Install a Nerd Font or set simpleline_nerdfont to 0.
Polling is unnecessary    Watched directories are not polled; check "git
                          watch:" in :SimpleLineHealth. If it says
                          "on/unavailable", run ./install.sh then
                          :SimpleLineRestart. Otherwise set
                          simpleline_git_interval to 0.
Changes arrive late       Set simpleline_git_watch to 0 if the worktree is on
                          a mount with unreliable change notifications; the
                          poll then runs everywhere again.
Need daemon errors        Set simpleline_debug to 1 and inspect :messages.
No remote segment         :SimpleLineHealth prints "remote workspace:";
                          "simpleremote absent" means the plugin is not
                          loaded, "disconnected" that nothing is connected.
                          The segment needs simpleline_show_remote (default
                          1) and a layout that lists "remote".
No visible statusline     Check 'laststatus' in :SimpleLineHealth; Simpleline
                          raises values below 2 and restores them on disable.

DAEMON SUPERVISION                                    *simpleline-daemon*

The Rust daemon is managed by simplecore, the supervisor shared by the whole
simple* plugin suite. It is vendored into this repository at
autoload/simpleline/core.vim; that file is generated, do not edit it in place.

What it guarantees:

- Liveness is always read from |job_status()|. job_start() returns a job
  object even when the exec itself failed, so a daemon that cannot start is
  never mistaken for one that is running.
- A superseded daemon's late exit callback cannot clear the state of the
  replacement that already took its place.
- Output still queued when you stop the daemon is discarded, so an explicit
  stop cannot be undone by an event that was already in flight.
- A daemon that dies is restarted automatically with exponential backoff.
  If it keeps crashing, the supervisor reports it once and stops trying
  rather than respawning forever; :SimpleLineRestart re-arms it.
- Requests orphaned by the crash, plus the current directory, are re-issued
  once the replacement has handshaked. Under g:simpleline_git_interval = 0
  the restart is the only refresh that will happen, so nothing is left
  showing pre-crash data.
- Requests are correlated to replies by id and can time out, so a wedged
  daemon never leaves a callback hanging.

:SimpleLineHealth
        Report daemon path, run state, negotiated protocol and capabilities,
        uptime, crash and restart counts, and whether the crash-loop breaker
        has tripped, alongside this plugin's own diagnostics.

                                                      *:SimpleLineRestart*
:SimpleLineRestart
        Stop the daemon and start a fresh one. Clears the crash-loop breaker,
        so this is the way back after repeated failures.

                                                      *:SimpleLineLog*
:SimpleLineLog
        Open the daemon transcript in a scratch buffer: start and exit events,
        restarts, protocol handshakes, send failures and stderr.

DAEMON COMMAND LINE                                    *simpleline-daemon-cli*

The daemon takes no arguments in normal use: the plugin starts it and speaks
JSON over its stdin and stdout.  For diagnosis it also answers: >

  simpleline-daemon --version
  simpleline-daemon --help
  simpleline-daemon --self-test
<
--self-test runs one request through the daemon in-process and prints "ok".
install.sh runs it on the freshly built binary before replacing a working one,
so a build that compiles but does not work never reaches lib/.

Every daemon in the simple* suite answers these three the same way.

VENDORED SUPERVISOR                                    *simpleline-simplecore*

The daemon supervisor in autoload/simpleline/core.vim, and the test harness
beside it, are vendored from the suite's shared .simplecore bundle rather
than written here — each plugin carries its own copy so that installing
this plugin alone is enough.  Do not edit those files in place: >

  make core-verify
